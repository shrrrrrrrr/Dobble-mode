## V1.3 — 本地账号与数据隔离（已完成）

### 功能范围

- [x] 本地账号注册 / 登录（用户名 + 密码，仅当前设备）
- [x] 按 `userId` 隔离作品、反馈、社区、资料（`creator-life-v2:data:{userId}`）
- [x] 旧版 `creator-life-v1` 数据的一次性导入提示（用户确认后导入）
- [x] 更新 README，说明当前认证边界与运行方式
- [x] 代码仓库推送到 `Dobble-mode`，打 `v1.3.0` 标签

### 明确不做

- 邮箱验证码、手机号登录、SMTP 配置
- Supabase 真实连接与云端同步

### 验收标准

- 可注册两个不同本地账号，数据互不可见
- 刷新页面后会话保持，退出后需重新登录
- `npm run build` 通过

## V2.0 — 云端数据层（代码已完成，云端激活待用户配置）

**目标：** 把私有数据同步到 Supabase，保留生活模式全部已有能力。

**认证决策：** 云身份采用路线图候选方案中的「邮箱+密码」（Supabase Auth），作为**可选云同步层**；本地账号保持不变。被否决的邮箱 OTP、手机号、伪造邮箱身份、自建密码后端均未采用。

### 功能范围

- [x] Supabase 客户端工厂（`src/services/cloud.ts`），无环境变量时云端整体关闭
- [x] 整账号状态快照同步：`app_state` 表（JSONB）+ owner-only RLS（`supabase/migrations/0002_cloud_state.sql`）
- [x] 云账号注册 / 登录 / 退出（邮箱+密码），入口在社区「我的」页面
- [x] 自动同步：登录后拉取较新一端（last-write-wins），保存后防抖推送
- [x] 手动「立即同步」；新帖时间改用标准时间戳（旧数据兼容显示）
- [ ] **用户侧：** 在 Supabase 执行 0002 迁移；`.env.local` 填入 URL + Anon Key；配置 Email provider 与重定向域名
- [ ] 多设备真机验收后打 `v2.0.0` 标签

### 设计取舍

- 采用整状态 JSONB 快照而非逐表映射：MVP 阶段零映射错误、天然覆盖专业模式/徽章等新实体；0001 的规范化表保留给未来真实多用户社区阶段。
- 图片仍以压缩 Data URL 存于状态内（每张 ≤~300KB）；`creator-media` 桶上传列入 V2.2 候选。

### 明确不做

- 专业模式 UI（V3.0 完成）
- 真实 LLM / Agent
- 跨平台自动抓数

## Git 版本管理约定

- **主分支：** `master`（生活模式主线）
- **标签：** `vMAJOR.MINOR.PATCH`，与上表里程碑对应
- **提交信息：** `feat:` / `fix:` / `docs:` / `chore:` 前缀，一句说清「为什么」
- **功能分支（可选）：** `feature/v1.4-weekly-recap` 等，合并回 `master` 后打标签
- **不推送至：** `creator-topic-library`（仅专业模式参考，保持只读）

## 当前阻塞项

1. **GitHub 推送：** 本机 HTTPS 存在自签名证书链问题，需检查代理/VPN 或改用 SSH + 已配置密钥后执行 `git push -u origin master --tags`。
2. **云端激活：** 需要用户提供 Supabase URL + Anon Key 并执行 0002 迁移（见 docs/DEPLOYMENT.md）。
3. **服务器部署：** 需要用户自己的服务器/域名（见 docs/DEPLOYMENT.md）。
